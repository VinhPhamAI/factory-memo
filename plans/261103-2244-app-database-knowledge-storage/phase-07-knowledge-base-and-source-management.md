# Phase 7 — Knowledge base and source management

Depends on phases 1–4 and proposed decisions D8, D9 and D10. The current API can only
list and create KBs. Sources can be added (upload, text, recording) but never removed,
and an identical file uploaded twice creates two sources.

## Scope

- View, rename and delete a KB.
- Add and remove a KB's files: the files a KB may use are its active sources.
- An identical file added twice to one KB gives one active source.
- Out of scope: per-user or per-KB access lists. The schema leaves "restricting
  individual collections to selected users" for later, and every active user can
  read every active KB.

## Contract

| Route | Role | Behavior |
|---|---|---|
| `GET /v1/knowledge-bases/{kb}` | any active user | `name`, `title`, `description`, `template`, `created_by` (username), `created_at`, `updated_at`; source counts by status; chunk counts by kind and status. 404 for an unknown or deleted KB. |
| `PATCH /v1/knowledge-bases/{kb}` | `expert`, `admin` | Changes `title` and/or `description` (D8). `name` is stable; sending it returns 422. Returns the detail. |
| `DELETE /v1/knowledge-bases/{kb}` | D9 | Soft delete (`deleted_at`). Returns 204; a second call returns 404. |
| `DELETE /v1/knowledge-management/{kb}/sources/{kind}/{source_id}` | D9 | Soft-deletes the source. Returns 204. 409 while a job of the source is `running`. |
| `POST /v1/documents/{kb}/uploads` | any active user | An identical active file returns 200 with the existing source `id` and `duplicate: true` (D10); a new file returns 201 as today. |

401 without a usable token, 403 for a role below the one listed, 503 when the
application database is unreachable.

## KB deletion

1. In one transaction, set `knowledge_bases.deleted_at`. Mark that KB's `queued` jobs
   `failed` with `KB_DELETED` and leave `running` jobs alone.
2. The worker checks the KB when it claims a job and on completion. A job of a deleted
   KB fails without retry and writes no chunks.
3. Search already excludes chunks of deleted KBs (phase 4). Chunks, sources, files and
   bytes stay, for history and citations.
4. The name stays reserved: the unique `name` index covers deleted rows, and phase 1
   tests pin this.
5. Notify the catalog listener so every API process stops serving the KB without a
   restart. Drop the KB's in-memory QA threads.

No restore endpoint in this phase; an admin restores with SQL if needed. A hard
delete is not offered.

## Source removal

- Set `knowledge_sources.deleted_at` and mark its `queued` jobs `failed` with
  `SOURCE_REMOVED`, in one transaction.
- Soft-delete its `files` row only when no other active source references the file.
  Bytes stay on disk.
- Chunks stay but drop out of search when no active source remains linked (the
  phase 4 filter). Conflict rows stay. The inventory hides removed sources; a
  `?include_removed=true` query shows them with `removed_at`.
- The original download returns 404 for a removed source, so file access follows the
  source, as the schema requires.

## One active source per identical file (D10)

Proposed enforcement: new nullable `knowledge_sources.original_sha256` (copied from
`files.sha256` for document and image sources). Add a unique partial index on
`(knowledge_base_id, original_sha256) WHERE deleted_at IS NULL AND original_sha256 IS NOT NULL`.

```python
async def create_upload(self, kb_id: UUID, file: NewFile, *, submitted_by: UUID) -> Created:
    """Record an uploaded file as a source, or return the active source with the same bytes.

    Returns:
        The new source and `duplicate=False`, or the existing source and `duplicate=True`.
    """
    try:
        return Created(await self.create(kb_id, kind=SourceKind.DOCUMENT, file=file,
                                         submitted_by=submitted_by), duplicate=False)
    except IntegrityError as exc:
        if violated_constraint(exc) != "ix_knowledge_sources_active_original":
            raise
    return Created(await self.active_by_original(kb_id, file.sha256), duplicate=True)
```

- The API removes the newly stored bytes when the result is a duplicate.
- A removed source does not block a new upload of the same bytes.
- Extraction keeps exact-content blocking across different files with the same
  converted text (`extraction_runs`).
- Typed text and recordings are not deduplicated here.

Schema work: an autogenerated revision for the column and index, the ORM field, and
`docs/architecture/database-schema.md`.

## UI (`frontend/src/pages/knowledge-management.tsx`, `knowledge-base-admin.ts`)

- KB header shows the detail fields and counts.
- For `expert`/`admin`: edit title and description; delete with a confirmation that
  requires typing the KB name. After deletion, the KB selector moves to another KB.
- Source list: remove action with a confirmation, disabled while a job runs.
- Upload result: a duplicate shows "File đã có trong KB" ("The file is already in the
  KB") and selects the existing source.

## First failing tests

- Detail returns counts for a KB with one source of each status; a deleted KB returns 404.
- `PATCH` by an `employee` returns 403; changing `name` returns 422; title changes
  show in the list.
- Delete fails queued jobs, the worker refuses a claimed job of the deleted KB, search
  returns nothing, and creating the same name returns 409.
- Source removal: the original download returns 404, its chunks leave search, a
  chunk also linked to an active source stays searchable, and a running job gives 409.
- Two concurrent uploads of the same bytes create one source; the second response
  is `duplicate: true` with the first ID, and the second object is removed from disk.
- After removal, the same bytes upload as a new source.

## Completion checks

- Repository integration tests and API tests pass; migration `upgrade`/`check` pass.
- In a running stack: rename a KB, upload a file twice, remove the source, delete the
  KB; the UI and QA endpoint stop showing it.
- Frontend build, lint and touched tests pass.
