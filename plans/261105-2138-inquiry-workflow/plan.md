# Inquiry workflow implementation plan

Status: all five phases completed, including docs. Implemented, nothing committed. Created 2026-11-05 from `main`
at `3f5c7de`; status updated 2026-11-05.

## Goal

An employee turns a chat into a self-contained inquiry, edits it and submits it
to an eligible expert. The expert accepts, edits, denies or asks for
clarification; the employee replies. Every review action is a permanent
`inquiry_events` row. Accepting never creates knowledge. Evidence stays readable
for the requester and assignee after the file leaves the library.

Scope: KISS. Features first; scale (pagination, notifications, multi-instance
locking) last and out of this plan.

## Starting point

- Tables `inquiries`, `inquiry_events`, `inquiry_files` exist
  (`backend/src/storage/orm/inquiries.py`, migration `2e755e6df2ca`). No API,
  service, store, agent endpoint or UI exists.
- `inquiry_events` is append-only by trigger (`3665f6870fa4`).
- Library deletion is soft; bytes stay on disk (`docs/features/file-library.md`).
- Chat answers carry no citations yet (knowledge search not connected), so draft
  evidence is mostly photos and library files until search lands.
- Supersedes `plans/261103-1436-agent-conversations/phase-04-inquiry-draft.md`.

## Confirmed decisions

- Drafts are `inquiries` rows with status `draft`; `assigned_to` is NULL only
  while `draft`. New column `submitted_at`.
- Expert eligibility: active, not deleted, role `expert`. Admin has no special
  role in this plan. One query serves `GET /v1/experts` and submit validation.
- Access: requester or assignee may open a submitted inquiry; only the requester
  sees a draft. Everyone else gets `404`.
- Transitions:

| From | Action | Actor | To | Event kind |
|---|---|---|---|---|
| `draft` | submit | requester | `open` | none; sets `submitted_at` |
| `open` | accept | assignee | `answered` | `accepted` |
| `open` | edit (content required) | assignee | `answered` | `edited` |
| `open` | deny (content required) | assignee | `closed` | `denied` |
| `open` | request clarification | assignee | `needs_info` | `question` |
| `needs_info` | reply | requester | `open` | `reply` |

  Any other combination returns `409 invalid_transition`. `in_review` is unused.
